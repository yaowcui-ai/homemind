## 1. 核心判断与建议定位

项目适合转向 AI 产品经理实习作品，不需要推倒重做。应保留已经实现的可运行底座，将后续重点从“完成全部技术模块”调整为“提出产品假设、做出取舍、实现核心旅程、用真实结果迭代”。

必须校准当前状态：现在是 **有账号隔离、持久化和规则联动能力的智能家居仿真控制台**。M1—M3 与 Figma→React 改版已完成；M4 只有细化设计；业务中尚无真实 LLM、单 Agent 或多 Agent 协作。不宜按页面数量、依赖包数量或阶段数量称“整个 AI 产品完成一半”。

建议目标定位：**HomeMind——把生活意图转为可解释、可核验联动任务的智能家居 AI 助手（仿真验证版）**。当前对外介绍仍须说明 AI 闭环待实现；实现并验证后再使用完整的 AI 产品介绍。

多 Agent 保留为可验证的差异化方案，而不是预先成立的产品价值。核心价值首先是减少组合指令的操作负担、保留用户例外、说明系统做了什么和没有确认什么；真实节电收益、真实家居控制效果尚无证据。

## 4. Figma、React 和用户旅程

### 4.1 Figma 已有成果

[现有设计文件](https://www.figma.com/design/Bo7Jqfnh4NNRQiMwNvXc2O) 有五个桌面页面、五个手机页面、手机注册态、十种交互/异常状态板、基础变量/文字样式和可编辑设备组件。页面覆盖概览、任务、配置、偏好、登录。React 已按批准方向落地，新增业务数据仍来自 API。

必须区分四层证据：可编辑图层、状态设计、可点击连线/状态转移、实际代码行为。前两层有记录；未找到完整原型连线证据，且本轮不能在线核验，因此“完整 Figma 交互原型已完成”不成立。自然语言、澄清、Agent 运行反馈和恢复分支也尚未形成实现。

Figma 开关列宽、手机时钟高度和非空房间删除禁用样式还待回写。React 已修正或保持正确行为，并有 360/390px 几何/交互检查。不要将画稿残留缺陷当成当前网页故障。参见 [改版记录](../verification/figma-redesign.md)。

### 4.2 已闭合和未闭合的流程

- 已有：注册 → 获取模板 → 修改配置 → 手动控制 → 读取结果 → 查看变化；偏好保存 → 新规则任务带入默认值；规则提交 → 动作结果 → 历史回看。
- 演示条件下可完成：未来温度目标 → 手动推进仿真 → 显式核验。它不是现实世界的自动预约或后台调度。
- 未完成：自然语言需求 → 必要澄清 → 目标/例外理解 → 受控计划 → Agent 执行反馈 → 结果/异常下一步 → 原任务继续与恢复。

### 4.3 最值得先解决的问题

1. **未来目标的连续操作负担。** 当前需要在任务与概览间切换、推进时间、重新选中任务、再核验；跨过目标分钟会缺证据。最小改动是在任务详情展示当前/目标仿真时刻与下一步，演示模式增加受控“推进到核验时刻”，保留独立核验语义。
2. **关闭调试后，未来目标没有推进路径。** 时间不后台流动，而 advance 又受 debug 开关限制。必须在 PRD 明确“仿真演示产品”的时间契约；不能靠一直等待或轮询假装真实预约完成。
3. **默认目标不保证可达。** 现有默认客厅 28℃、回家 26℃、20 分钟、低风速，对应测试预期就是目标时刻 partial/failed。应选明确可演示的默认配置，或提示可达性/失败原因；不能放宽评分，把设温成功当成按时降温成功。证据：[既有回归](../../backend/tests/test_m3_tasks.py)。
4. **任务历史有，任务连续性不足。** 切视图/刷新会丢失 selected task；未知提交的幂等恢复只在当前 Workspace 内存中保留。优先补账号隔离的任务定位与“结果待确认”恢复入口，不盲目重复动作。
5. **模板目标过于绑定设备组合。** 规则将灯、帘、空调都列为所需设备，“只关灯”无法自然表达。PRD 需明确用户必需目标、可选动作、保留约束，之后再调整规划语义，不随意将现有行为判成代码 bug。
6. **界面更像工程控制台。** 首屏统计、调试时钟、传感卡优先于设备和任务；新用户缺少可跳过的准备清单。是否重排必须用任务观察验证，不再次整体换皮。

## 9. AI 产品方案需要讲清楚的取舍

### 9.1 用户和价值假设

候选目标用户：有灯光、空调、窗帘联动需求，但不愿配置复杂规则的个人居住者或小家庭中的单一操作者。当前账号模型仍是一人一家庭，不扩共享成员。

待验证问题：组合需求和例外是否难于现有场景按钮表达？用户能否理解“设置成功、目标待核验、读数未知”的区别？是否愿意为自然语言输入承担模型延迟？这些尚无用户证据。

最小研究建议：可招募 3—5 位符合候选画像的体验者，记录是否有真实智能家居使用经验、原有控制方式、任务操作和误解；本人自测单独标识。招募不到时明确记未开展，不用 AI 模拟访谈冒充真实调研。小样本只能发现可用性问题，不能代表市场规模或总体偏好。

### 9.2 为什么可能需要多 Agent

- 固定、明确任务：规则足够，模型不应增加无价值开销。
- 明确单目标自然语言：单 Agent 理解和规划，并共用确定性执行器。
- 多目标冲突：例如“提前达到舒适温度，同时尽量降低模拟能耗并保留指定设备”，再验证是否值得引入专业建议。
- 舒适 Agent 提可达性/舒适方案，节能 Agent 提模拟能耗/替代方案；均只读。
- 协调 Agent 根据用户明确约束和软目标优先级整合，硬约束互相冲突时向用户澄清，不静默牺牲例外；只有统一执行器写设备。

多 Agent 的潜在价值是不同目标的显式审查与可解释取舍，潜在代价是延迟、token、方案冲突和调试负担。只有实际对照支持的任务才成为默认路由；如无优势，可以保留实验入口、默认单 Agent，报告结论本身仍有产品经理求职价值。

### 9.3 风险与反馈策略

读取状态不必确认；用户明确要求的低影响单设备操作走短流程；全屋批量、更改已有手动设置、范围不确定或例外冲突需按影响预览/确认或澄清。不要给每次开关灯增加多轮确认。

当前不支持的门锁、燃气等高风险设备应拒绝，不能为展示风险控制新增这类真实能力。权限、参数、窗户和保留/保护约束由程序执行，不只写在提示词里。计划事实过期时停止并解释；自动重规划在用户价值明确时有限加入。

先用可理解的任务阶段和手动/低频读取反馈，不要求先建设完整 SSE；但执行中、等待输入、等待目标核验必须区分。模型调用/工具/超时有上限，历史回看不再调用模型，未知用量不写零。真实调用有成本，批次先列数量和预算，不默认开展付费评测。

## 10. 效果评测与迭代建议

软件用例通过数不是 AI 产品效果。应从真实运行保存初始配置、输入、期望目标/约束、输出、动作/读回、最终状态、调用/用量、耗时、失败原因和版本。

| 指标 | 建议口径 |
| --- | --- |
| 指令理解准确率 | 场景、对象、温度/时间、保留/保护全部匹配标注的指令数 / 需要解析的指令数；格式非法计失败 |
| 目标完成率 | 在约定核验条件下全部必需目标满足的运行数 / 预先标注应可执行的场景运行数；失败、未知、触预算都不算完成 |
| 多设备联动成功率 | 全部必需设备动作独立读回符合目标的运行数 / 应联动的运行数；不等于环境温度达标 |
| 约束违规率/假成功 | 越权、改保留设备、违反保护、未知状态下违规控制；把未完成说完成的次数。目标为零，但有限样本不能证明全局零风险 |
| 异常处理正确率 | 预标注应澄清、拒绝、标记未知或保持不重发的场景中实际行为正确的比例；与任务完成率分开 |
| 交互负担 | 澄清轮数、不必要澄清、误操作、完成人工步骤/耗时；与表单基线同任务比较 |
| 响应与成本 | 首个有效反馈/规划/执行分别计时，报告 P50/P95 和样本数；人等候和仿真时间单列；记录调用/token，未知成本如实标注 |

最小初始方案可建议 12 个开发场景 + 12 个冻结验收场景，覆盖正常、例外、歧义、冲突、故障、配置变化六类；再对提前选定的代表场景重复运行。数量是建议，不是已完成样本。原 30/20 方案可在有必要时扩展，不为追求规模提前消耗预算。

比较要拆两层：自然语言理解只评具备该能力的方案；执行/规划对照选规则、单 Agent、多 Agent 共同支持的同目标子集。规则表单不具备自然语言理解，不能因此制造“AI 比规则理解率更高”的结论。三方案使用同初始状态、能力、硬约束和核验条件；单/多使用同模型配置并披露预算与实际消耗，不能给多 Agent 隐藏额外事实。

开发/验收集先分开，验收条件预定，保留全部失败和原始结果。小样本结果只支持所测任务，不写“显著优于”或市场普适结论；不开展没有流量条件的假 A/B 测试。仿真 Wh 可作同模型内相对比较，不能外推真实节电率。

迭代台账每条只需：问题及来源 → 影响哪个目标 → 备选方案/取舍 → 实际修改 → 同口径复测 → 残余限制。可复用真实案例：deadline 证据、未知提交幂等、跨标签隐私与草稿、移动端长名、Figma 开关/时钟到代码修正。它们是工程/体验问题来源，不能说来自未开展的用户访谈。

## 12. 简历和面试能讲什么

当前可以真实展示：

1. 对回家、睡眠、离家场景做范围和业务规则设计，落地可配置的仿真产品，而不是只有聊天输出。
2. 通过 Figma 与 React 完成桌面/手机可操作界面，包含账号、家庭、设备、任务、历史、偏好与异常。
3. 区分“设备动作完成”和“用户目标达到”，将未知、失败和例外转化成验收条件；有规则、读回和回归证据。
4. 从真实缺陷到方案和回归的迭代经历，包括手机布局和重复提交等；可如实说明使用 AI 辅助开发。

当前简历示例（个人职责需按实际参与再调整）：

> 围绕回家、睡眠、离家三类场景，规划并借助 AI 辅助开发完成智能家居仿真产品原型，覆盖独立家庭配置、设备控制、规则任务及历史；完成 Figma 到 React 的桌面/手机界面交付。
>
> 制定设备动作与环境目标分离的核验方式，覆盖保留设备、房间保护、读数未知和响应丢失等异常，并以自动化测试及手机操作检查验证核心流程。

完成后才可增加：真实自然语言/澄清/多 Agent 能力、实际用户研究、同条件单/多 Agent 对照、任务完成率/时延/交互负担结果。没有数据时不填提高百分比。未上线、未接硬件，不写线上用户量、真实节电、生产部署或全屋自动化。

项目能证明个人如何定义问题、取舍方案、组织 AI 辅助实现、制定验收并解释失败；不能自动证明真实公司跨部门协作、商业增长或团队管理经历。
