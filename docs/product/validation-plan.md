## 2. 最小用户研究：招募与方法

建议招募 3—5 位有实际智能家居控制经验、能回忆近期操作的人，记录其设备数量级、使用频次和是否有联动经验。条件不符的参与者仍可用于可用性观察，但单独标为新手，不混称目标用户。本人 U01 单独标识，不包装成第三方访谈。

本阶段只准备提纲，不代用户联系或招募。先说明项目是仿真，征得记录同意；按匿名参与者编号保存，不收真实账号、住址或密码。招募不到则标记未开展，不生成虚构访谈或引语。

访谈提纲（先了解过去行为，再展示方案）：

1. 最近一次使用了什么设备？为什么要控制它？按顺序回忆实际操作。
2. 最近一次同时控制多个设备是什么时候？如何做，有没有中断或没达到预期？
3. 是否遇到临时保留某盏灯/不动某个房间？当时怎么处理？没有也如实记录。
4. 怎么判断操作生效？看到“空调已设26℃”时，你认为能说明什么？
5. 展示原型后，请参与者复述理解和担忧；不先告知“AI更省事”或诱导其认可多 Agent。

可用性观察建议四个任务：明确单灯控制；带保留项的回家/睡眠安排；同名对象澄清；解释部分完成并继续核验。先使用当前可用规则/UI；未来能力只有在真实实现后才能观察，不能拿讲解替代实际操作。跨入口比较轮换顺序，避免所有人先熟悉一种入口后再测另一种。

每次记录：参与者标签/同意 → 原始任务和初始状态 → 实际步骤/耗时/求助 → 可核对原话/观察 → 研究者解释 → 对应 H/R 编号 → 候选修改。事实、引语、解释和建议分栏；演示者代操作不能记作独立完成。

小样本主要发现问题，不推导市场规模、统计显著性或普遍满意度。没有真实流量条件时不声称完成线上 A/B 测试。

## 3. 开发场景草案

以下 DEV01—DEV12 是给阶段 B 的可读开发用例，不是已执行结果，也不是冻结保留集。每次运行需记录实际 home/world/config/state 版本与动态 ID；名字用于阅读，不允许执行器依赖写死的“客厅”ID。存在多种合理方案时，按目标/约束集合验收，不机械匹配动作顺序或模型文案。

| DEV03 | 两房部分灯和空调已开；“离家，关闭全屋灯和空调，合上窗帘” | 当前清单内生成全部必需动作，逐项读回，不能遗漏修改后的实体 | R02/R04/R11 |
| DEV04 | 客厅主灯已开，其他设备状态已记录；“只关闭客厅主灯，其他设备保持原样” | 仅该灯写操作；不附加空调或窗帘动作；规则基线不支持时标覆盖差异 | R02/R04 |

| DEV08 | 卧室主灯已开；“同一盏主灯既必须关闭，又必须保持开启，两条都不能忽略” | 说明冲突并询问，不静默选择，不产生写动作 | R03/R04 |
| DEV09 | 客厅窗户主读数未知；“客厅开空调制冷到26℃” | 不发送违规制冷，不当作窗户关闭；解释缺证据和下一步，不虚构关窗能力 | R04/R05/R08 |
| DEV10 | 主灯注入响应丢失；“关闭客厅主灯” | 区分响应未知与独立读回，匹配时确认动作；不靠重复发送证明成功 | R04/R05/R06 |

## 4. 数据划分与公平比较

先使用12个开发场景完善实现；另准备12个独立验收场景，在最终模型、提示词、初始状态、目标/评分契约确定后冻结并记录文件摘要。本轮没有编造保留集内容或声称已经冻结。保留集一旦用于调优应转为回归，并另设保留样本。

对照分两层：

- 意图理解：单/多 Agent 从原始自然语言解析；规则表单无此能力，标不适用，不能给其理解率记零来制造优势。
- 规划/执行：三方案使用共同支持的同目标子集、同初始配置/状态/故障及硬约束。规则需要的人工表单输入单独说明。不能在比较时默默修改原规则成功条件或给多 Agent 额外事实。

单/多Agent对照计划使用相同模型配置，披露预算与实际消耗；先整体验收一次，再对预选3个代表场景各补跑2次，使这些场景共3次。每次保留，不挑最好结果。样本数、方案数、重复数、调用上限和费用依据须在对照前列明，目前未授权实际对照批次。C的40次单Agent开发验证是独立已完成批次，不套用这里的重复设计。

用户操作负担与系统算法效果分别报告：表单填写时间属于用户体验；服务端执行耗时属于系统性能。模拟能耗仅在相同物理假设下比较，不推导真实节电或舒适度提升。小样本允许得出收益有限、无优势或部分退化，不能称“显著优于”。

## 5. 指标、分母与记录

| 指标 | 计算/记录口径 | 不计作成功的情况 |
| --- | --- | --- |
| 指令理解准确率 | 对象/范围/温度时间/保留保护全部正确的指令数 ÷ 需解析指令总数；多轮原始与澄清后结果分别报 | 格式非法、漏例外、猜对象；不能只统计解析成功者 |
| 目标完成率 | 全部必需目标在约定条件下核验通过的运行数 ÷ 预先标为应可执行的场景运行数 | failed、partial、unknown、超预算、超时、还在等待；不按结果事后移出分母 |
| 联动动作成功率 | 全部必需设备动作读回匹配的运行数 ÷ 应联动运行数 | 只有设备响应成功；此项不替代温度等环境目标 |
| 异常处理正确率 | 应澄清/拒绝/标未知/保持不重发的场景中，行为符合预标注要求的运行数 ÷ 对应场景运行总数 | 正常任务全部拒绝；合理拒绝不混入目标完成分子 |
| 约束违规/假成功 | 逐次记录越权、改保留项、违反保护/能力/窗户约束、未完成却报告完成 | 任何已知关键违规都应阻断交付；有限样本为零不是全局保证 |
| 交互负担 | 人工步骤、澄清轮数、不必要澄清、完成时间、求助/误解，附样本来源 | 演示者代操作、提前讲解答案或混入本人自测 |
| 时延 | 请求到首个有效问题/计划/结果，以及模型规划、执行各阶段墙钟耗时；人等候与仿真分钟单列 | “正在处理”不能冒充有效结果；只报成功请求会隐藏失败等待 |
| 调用与用量 | 请求/失败/重试实际次数，返回token及模型标识；无用量时标未知 | 未返回用量记零、没有价格依据却估精确费用 |

所有比例附样本数、分子分母与模式；报总体和场景类别结果，不能用平均值遮盖冲突/异常短板。时延报告 P50/P95 时注明有效样本与失败/超时计数，使用最近秩法（排序后取ceil(p×N)），小样本P95通常接近最大值，应明确限制。

每次运行最少保存以下字段（字段为产品记录要求，不代表当前 API 已全部提供）：

`run_id / case_id / split / repeat / actual_mode / source(real_model or controlled_test) / app-prompt-model-config版本 / home-world-config-state版本及初始快照 / 原始需求和澄清 / 预期目标与约束 / 公开计划 / 实际动作与读回 / 目标核验证据与时间 / 最终状态 / 耗时与调用用量 / 评分与失败分类 / 原始证据路径`

不保存密钥、密码、完整连接串或私有推理。不能用模型自述成功替代动作/传感证据。协议成功、动作成功、环境目标成功、异常处理正确分别判断。

失败分类：理解/定位、澄清策略、计划或约束、设备/读回、时间证据、状态过期、接口/模型、交互/恢复、评测脚本。评测脚本失败单列，修正后保留原始运行再复测，不冒充产品故障或删掉坏结果。

## 6. 阶段出口与当前结果
