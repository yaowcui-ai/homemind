# HomeMind：智能家居多 Agent 协同调度系统设计

日期：2026-10-26（Asia/Shanghai）

状态：总体设计 v1 已由用户确认，作为后续分阶段开发基线；实际开发进度以路线和项目接续记录为准。

开发入口：[分阶段开发路线](../../homemind-development-roadmap.md)。默认配置：[十二实体设计](2026-10-26-homemind-default-entities-design.md)。

## 1. 已确认的方向与协作方式

- 做适配电脑和手机浏览器的网页系统，电脑端重点展示协作与执行过程。
- 仿真设备优先；真实设备接入作为 v1 交付后的扩展。
- 支持多账号，每个账号拥有一个独立仿真家庭；默认两房十二实体，用户可以修改房间和实体配置。
- LangGraph 为核心，LangChain 按需提供模型、消息、工具和结构化输出组件。
- 使用 React、TypeScript、Python、FastAPI、MySQL、SSE 和 Docker Compose。
- 不增加名为 Harness 的框架或单独开发项目；评测以仿真场景和 Python 脚本完成。
- 用户逐阶段发起开发；助手负责该阶段的设计细化、编码、必要验证和修复。
- 不沿用旧项目中“首次核心代码必须由用户手写”的教学分工。需要理解的核心机制仍须简洁解释。
- 每次只完成用户指定阶段。用户的问题和修正作为当前阶段的补充；阶段内已授权的常规工作不逐文件重复确认。

## 2. 产品目标与 v1 范围

系统将生活需求转为可核验的设备动作，协调舒适与节能目标，处理环境变化与设备故障。

默认模板包含客厅、卧室两个房间，共 12 个实体：每个房间有灯、空调、电动窗帘、温度传感器、人员占用传感器、窗户状态传感器。可控实体 6 个，只读传感实体 6 个。注册时复制为用户自己的家庭，分配独立内部 ID 和运行状态；数量是默认配置，不是写死的全局家庭或容量上限。具体能力、初值及增删规则以十二实体设计为准。

用户通过表单管理房间与实体，无需上传户型图。第一版支持六种已实现类型的实例增删、改名、迁移和停用；普通家具、精确坐标、图像识别及三维布局不在范围内。设备归属变更或移除会使相关旧计划失效，历史仍保留快照。

v1 只完成三个场景：

| 场景 | 示例需求 | 核验重点 |
| --- | --- | --- |
| 回家准备 | 二十分钟后回家，客厅舒服一点，卧室有人睡觉，尽量省电 | 客厅目标、卧室限制、目标时刻与仿真假设 |
| 睡眠模式 | 卧室凉快一点，关灯拉帘，保留客厅灯 | 组合动作、例外保留、明确的温度目标 |
| 离家模式 | 我要出门，关掉不需要的设备，卧室空调保留 | 关闭范围、保留项、部分失败 |

演示输入、初始家庭状态和预期条件必须对应。示例场景中的温度目标属于用户确认的偏好或明确输入，不能由模型凭空视为硬性要求。

v1 不包含语音、视频理解、原生手机应用、品牌全兼容、自研物联网协议、向量知识库、自动学习偏好或复杂真实时间调度。“二十分钟后”使用可控仿真时钟；准备动作可立即开始，目标时刻由仿真推进到达，不宣称已实现真实世界的后台预约调度。

| 层 | 选择 | 责任 |

| 数据访问 | MySQL 8.4、SQLAlchemy、Alembic、asyncmy | 业务记录、事务、数据库迁移 |

| 通信 | HTTP 提交命令，SSE 推送事件 | 任务和设备状态同步 |
| 验证 | pytest、HTTPX、Vitest、React Testing Library、Playwright | 业务、接口、交互和关键流程验证 |

| 发布 | Docker Compose、Nginx | 独立后端、网页入口、数据库与持久卷 |

具体依赖在第 1 阶段进行兼容性验证并锁定。MySQL 检查点包是社区实现，不标为 LangGraph 官方 MySQL 存储；第 1 阶段检查依赖兼容，第 6 阶段以重启恢复验证其行为。若不兼容，先报告具体证据和可选方案，不静默替换数据库或自行扩展存储框架。

新应用目录拟为工作区中的 `homemind/`。它使用自己的依赖、配置、数据库、容器和卷。既有 DocTrace、售后项目、MySQL 服务与数据不作为可修改对象。模型密钥由用户配置到新项目自己的环境文件，禁止从旧项目私有配置自动复制。

本地开发端口拟为前端 5174、API 8100，交付网页入口拟为 8088；第 1 阶段检查占用。已有服务不为新项目让路，发生冲突时为新项目选择空闲端口并记录。数据库优先运行在新 Compose 项目的内部网络，不默认映射主机 3306。开发服务通过终端命令启动，部署阶段增加经过核验的启动和停止说明。

## 4. 模块边界

1. **网页**：显示状态、配置家庭并提交命令；设备是否执行成功由服务端事实决定。
2. **账户与任务服务**：注册登录、家庭归属校验、房间与实体配置、任务接收与幂等、状态管理、持久化事件和历史查询。
3. **LangGraph 工作流**：识别目标、决定是否协作、收集建议、协调、校验、执行、核验及有限重规划。
4. **专业 Agent**：按职责读取相关状态，返回结构化建议。
5. **规则与执行模块**：执行参数校验、范围限制、状态版本检查与统一设备写入。
6. **设备接口**：提供读取快照、执行绝对状态动作、查询结果和获取能力描述。仿真与真实设备使用同一边界。
7. **仿真环境**：管理时间、设备、传感器和故障；评测能重置为固定初始状态。
8. **持久化**：分别管理业务事实、动作记录、事件和运行检查点。
9. **场景评测**：独立调用任务入口，依据环境事实判定条件，不将系统自述成功作为得分依据。

每账号一个家庭，核心数据关系为用户、家庭、房间、实体、任务、动作和事件。家庭 ID 由认证上下文验证，模型不能通过传入其他家庭或实体 ID 扩大权限。配置、设备操作、历史、SSE 和检查点命名空间都必须隔离，不能仅依靠前端过滤。初期数据库可保存多家庭，v1 不增加家庭成员共享或多住宅管理。

先做一个模块化 Python 后端。v1 同一家庭最多执行一个会修改设备的任务，其他提交返回家庭忙碌说明；界面手动修改和仿真事件仍可改变状态，用于检验过期计划。多 Agent 的只读分析可并行，设备写入统一串行。v1 部署限定单执行进程，不能据此声称支持多个 API worker 下的分布式调度。

## 5. Agent 职责与工作流

| Agent | 输入 | 输出 | 写权限 |
| --- | --- | --- | --- |
| 协调 Agent | 需求、偏好、家庭快照、专业建议、失败事实 | 目标拆解、所需参与者、候选计划与简要依据 | 无直接设备写权限 |
| 舒适 Agent | 相关房间温度、占用、睡眠限制、设备能力 | 舒适目标、候选动作、假设与冲突 | 无直接设备写权限 |
| 节能 Agent | 相关设备、占用、功率参数、仿真时刻 | 节能候选动作、与目标的取舍、估计依据 | 无直接设备写权限 |

不同 Agent 可使用同一个已验证的模型。模型服务必须先通过工具调用、结构化输出和错误响应的最小检查，不能仅凭接口格式兼容就宣称能力兼容。

基本数据流：

`接收需求 → 读取快照和偏好 → 识别目标 → 路由 → 形成候选计划 → 规则校验 → 执行前状态核对 → 统一执行 → 核验 → 保存结果`

路由分为：

- 明确单设备动作：短流程，不调用两个专业 Agent。
- 需要舒适与节能协调的任务：专业 Agent 基于同一版本快照提交建议，协调 Agent 整合。
- 信息不足或要求相互矛盾：进入等待补充状态；用户回答后回到同一个任务，不生成隐式新任务。
- 执行前状态变化或可恢复失败：根据真实反馈有限重规划。

规则先约束动作是否合法、是否属于当前家庭及用户权限，再检查用户明确限制和已确认场景偏好。明确要求互相矛盾时请求澄清，不能通过自行降低其中一项的优先级掩盖冲突。舒适和节能均为软目标时，按保存的偏好排序；不存在对应偏好时询问。

专业建议和最终计划必须是经 Pydantic 校验的结构化对象，包含目标、涉及实体、快照版本、动作、前置条件、成功条件和简要依据。页面展示可核查的决策摘要，不要求记录模型内部思维过程。

## 6. 仿真、时间与效果判断

- 仿真时钟由显式推进命令驱动；普通读取不推进时间，重试也不隐式推进时间。
- 相同初始快照、动作序列、故障脚本和时间推进序列，必须得到相同环境结果。
- 温度变化与能耗采用版本化的简化模型，参数可记录、可复现；物理规则、设备范围和时间步长在第 2 阶段的独立设计中固定后实现。
- “动作已生效”和“环境目标已达到”分别记录。例如设温 26℃成功，不代表当前室温已到 26℃。
- 目标时刻尚未到达时，页面显示已执行动作与待核验条件。推进到目标时刻后才评价对应环境目标。
- 仿真能耗按设定模型计算，单位和时间范围明确；只报告仿真内比较，不外推为真实家庭节电比例。
- 故障至少包含：设备离线、返回延迟、执行前失败、动作已生效但响应丢失、动作返回成功但状态未改变。
- 每次 reset 生成新的环境实例标识。旧任务不能继续向重置后的环境写入，历史记录保留原实例标识。
- reset 只重置该家庭的运行状态，保留用户当前房间、实体清单和偏好，不重新创建已移除的默认实体。房间配置与设备配置也纳入可复现快照。
- 有人传感器不判断睡眠，窗户传感器不具备关窗能力；Agent 不得虚构这些感知或执行能力。传感器缺失、离线或未知不能当作空房、关窗或已达到温度目标。

## 7. 任务、动作、事件与恢复

任务状态统一为：`queued`、`running`、`waiting_input`、`waiting_verification`、`succeeded`、`partial`、`failed`、`cancelled`。

- 同一任务状态变化使用显式转换规则。进入等待补充或等待目标时刻核验时释放家庭执行占用；继续时重新获取占用并检查环境版本。
- `succeeded` 表示当前任务定义的所有必需条件已核验；`partial` 表示部分必需动作/条件完成且存在失败或无法确认项。
- `queued` 在 v1 表示已受理、等待该进程调度；并发写任务受家庭占用限制，不宣传为分布式队列。
- 取消在动作边界检查，停止后续动作；已发生动作仍记录，不以取消等同自动回滚。
- 恢复和继续都沿用 task_id，检查点线程使用包含家庭和任务的独立命名空间。

动作使用 `planned`、`submitted`、`verified`、`failed`、`unknown`、`skipped`。执行器优先调用设置绝对目标状态的动作，如 `set_light(false)`，避免重试 toggle 产生反向效果。

每个任务有请求幂等键和规范化请求摘要；同键同内容返回原任务，同键不同内容拒绝。动作有唯一 action_id，执行前写入动作意图。外部设备与数据库之间不假设存在原子事务：响应丢失或进程中断后先核对设备现状，再决定是否继续、重试或标记无法确认。

状态核对基于动作涉及实体的预期版本与前置条件。任务自己完成的动作更新任务内的预期版本，不能被误判为外界修改。用户手动控制或其他外界变化使相关计划过期时重新规划；默认最多 2 次重规划，默认最多 12 次模型调用、单次调用 30 秒超时、一次活跃执行 180 秒时限，均为可配置初始上限并写入报告。等待用户或仿真时钟的时间不计入活跃执行时限，恢复后累计模型调用和重规划次数，不通过续跑清零预算。

SSE 传输的是先持久化的事件。每个任务具有单调事件编号，断线后按 Last-Event-ID 补发，客户端去重。事件流断开不代表任务失败，也不自动再次提交任务。快照与事件都带版本，旧事件不能覆盖更新的设备状态。

LangGraph 检查点用于恢复图状态；MySQL 业务动作记录用于判断设备副作用。历史详情页只读已保存记录，不恢复图、不调用模型。

## 8. 网页与基本账户

网页至少有五个视图：

1. 家庭控制台：当前账号的房间、设备与传感器状态、手动控制、时间推进与故障设置。
2. 任务交互：需求、澄清、结构化建议、最终计划、步骤进度和目标核验。
3. 任务历史与详情：初始状态、偏好版本、事件、执行结果和最终快照。
4. 偏好设置：舒适范围、睡眠限制、保留设备和软目标优先级；修改后生成新版本，已保存任务保留原版本。
5. 家庭配置：首次使用模板说明，房间增删改、实体增删改和迁移；只允许配置已有类型及其合法参数。

前端初期允许明确标注的静态演示数据；接入真实后端后，不能继续用静态状态冒充实时设备或 Agent 结果。

第 2 阶段先实现可配置家庭模型，第 3 阶段接入注册、登录及家庭隔离：创建账号时仅初始化一次其家庭与独立模板。采用 HttpOnly Cookie 会话、密码哈希及写请求来源/CSRF 防护；状态、任务、SSE 和调试接口统一校验会话。第 7—8 阶段完善配置向导与页面体验。v1 支持多账号独立家庭，不扩展复杂组织权限、共享成员或多住宅平台。故障注入与 reset 限本家庭并属于调试功能，交付默认关闭，演示模式显式开启。

## 9. 测试、对照评测与完成标准

程序验证覆盖：设备合法动作、仿真可复现、家庭隔离、房间/实体配置变更、缺失传感器、规则限制、状态过期、动作未知结果、幂等、检查点恢复、取消、预算终止、事件补发和页面关键操作。模型输出用可控替身测试程序分支；模型真实效果通过场景评测单独验证。

规则基线、单 Agent 和多 Agent 使用相同的设备接口、规则、初始环境和故障脚本；单/多 Agent 使用相同模型配置并记录实际调用与预算消耗。协调流程可能不同，但不能通过给某一方案隐藏额外事实制造优势。

场景集为 30 个开发场景和 20 个保留场景，分别覆盖普通需求、限制例外、目标冲突、信息缺失、状态变化和设备故障。调优只使用开发集；保留集的内容与评分条件在运行前冻结，若用于后续调优则转为回归集，另建保留集。

场景还需覆盖用户修改默认配置后的任务，包括房间改名、新增房间/灯、移除空调或温度传感器；总场景数保持不变，将这些变体分配到开发和保留场景中。同一对照任务的三种方案仍使用相同配置，不能只对其中一种方案修改设备。

评分以仿真状态与动作记录为主：任务必需条件达成率、硬约束违反、无效/重复动作、故障处理结果、耗时、模型调用及可获取的 token/费用信息。拒绝正确执行不等于成功，合理澄清单独评分；到达调用预算上限的停止也不计作目标完成。供应商未返回用量时标记未知，不能写成零。

先运行冻结保留集一次，再对提前选定的冲突与故障代表场景以相同条件重复 3 次，报告模型波动和额外成本。允许结论是多 Agent 仅在部分复杂场景有收益，也允许单 Agent 在简单任务更高效。

v1 完成必须同时满足：

- 三个场景有正常、例外、冲突与故障演示；简单任务采用短流程。
- 至少两个账号独立使用各自家庭；可修改默认房间和实体；跨家庭读写拒绝，配置变更与历史保留有实际验证。
- 已完成独立部署、数据持久化、关键恢复与事件补发检查。
- 关键约束、未知结果核对、幂等和预算终止测试通过。
- 有规则/单 Agent/多 Agent 的可追溯对照结果及局限说明。
- 可在电脑和手机宽度完成关键操作，没有遮挡输入和主要控制按钮。
- 有启动停止、配置、备份恢复、架构、演示和面试材料。
- 简历内容对应实际完成的代码与记录，不宣称真实硬件、生产规模或未测得的性能。

## 10. 阶段与后续变更

2026-10-26，用户确认当前设计。总体设计阶段完成，下一阶段为 M1 工程基础。确认范围包括网页形态、多账号独立家庭、可编辑两房十二实体模板、仿真存在信号、三个业务场景、LangGraph 主导、受控执行与对照评测。

依赖精确版本、目录组织、API 字段、数据库迁移、仿真公式和页面布局分别在对应阶段开始时细化，并在该阶段实施前形成计划。它们属于已规划的实施细节，不要求在启动 M1 前完成后续所有阶段设计。新增业务范围须由用户提出或确认。

开发按路线文档 M1—M10 推进，每阶段开始前只细化该阶段的文件、接口和验证步骤；其细化设计不得改变本规范已确定的范围和职责。完成后记录证据与未实现项，由用户发起下一阶段。

真实设备接入为 M11 扩展：通过统一设备接口增加 Home Assistant 适配器，先接少量设备，用真实读回结果验证；硬件选择、真实网络和运行条件在该扩展开始时确定，不计入 v1 完成条件。

## 11. 参考依据

- [LangGraph 持久化与检查点](https://docs.langchain.com/oss/python/langgraph/persistence)：检查点状态与跨任务数据的职责不同；内存检查点不具备重启持久化。
- [社区 MySQL 检查点适配器](https://pypi.org/project/langgraph-checkpoint-mysql/)：支持 asyncmy，需要结合所选 MySQL 和 LangGraph 版本实际验证。
- [FastAPI SSE](https://fastapi.tiangolo.com/tutorial/server-sent-events/)：用于服务端事件推送。
- [Home Assistant REST API](https://contributors.home-assistant.io/core/internals/rest-api/)：作为后续真实设备适配边界的依据。
