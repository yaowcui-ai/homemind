## 1. 模板与用户家庭

每个注册账号在自己的家庭中获得一份独立的默认模板：客厅、卧室两个房间，共十二个实体。用户可以增加、重命名和删除房间，增加、移动、停用和移除已支持类型的实体；两个房间和十二实体是初始配置，不是系统容量上限。

第一版每个账号管理一个家庭，不增加家庭成员邀请、多住宅切换或自定义设备驱动。实体清单及所有状态、偏好、任务、检查点和事件按家庭隔离。相同模板生成的两个家庭不能共享可变状态或动作目标。

模板中的名称和下表模板键用于初始化与示例。复制到家庭时，为房间和实体生成独立且不可变的内部 ID。用户改名或移动实体不改变其内部 ID；工具调用与历史引用使用内部 ID，并始终校验家庭归属。

“实体”表示一个可查询状态的功能或数据点，可能用于控制，也可能用于感知。本模板共有六个可控实体、六个只读传感实体。它不等于十二件实体硬件，也不包含普通桌椅、沙发等无关物品。

## 3. 六种实体类型的能力边界

### 3.1 灯

- 状态包括开关和实际亮度百分比；亮度范围为 0—100 的整数。
- 亮度 0 表示关闭；开启状态的亮度必须为 1—100，不能同时报告开灯和实际亮度为 0。
- 单独开灯时使用该实体保存的默认开灯亮度；关闭不抹去此偏好。
- 第一版不包含色温和 RGB。没有照度传感器，不能宣称已测出房间是否足够明亮；“亮一些”可按用户确认的相对亮度调整，并读回灯的亮度状态。

### 3.2 空调

- 第一版只支持 off 和 cool，不将制热、除湿、送风模式或新风列为默认能力。
- 目标温度范围为 16—30℃，步长 1℃；风速支持 low 和 auto。
- 控制目标温度、设备工作模式和房间实测温度分别保存。将目标设为 26℃并核验成功，不等于室温已达到 26℃。
- 当前制冷/待机状态由仿真器按房间温度、目标温度和已固定的规则确定，模型不能自行改写该状态。
- 风速 low 可作为已确认睡眠偏好的动作之一；系统没有噪声传感器，不承诺或报告实测噪声分贝。
- 空调对室温及能耗的影响在 M2 固定为可复现的简化模型；温度变化只能由该模型、合法仿真事件或时间推进产生。

### 3.3 电动窗帘

- 开度范围为 0—100 的整数，0 为完全关闭，100 为完全打开。
- 打开/关闭操作分别映射为目标开度 100/0；执行器读回开度验证结果。
- 关闭窗帘不改变窗户传感器状态。遮光和热增益效果属于仿真模型假设，不能作为真实测量。

### 3.4 温度传感器

- 提供摄氏温度、读数时间和数据质量；显示精度为 0.1℃，内部仿真精度与舍入规则由 M2 固定。
- Agent 只读。用户在仿真控制页设置初始温度或注入环境变化，属于仿真权限，不是暴露给 Agent 的工具。
- 默认一个房间绑定一个主温度读数。用户增加多个温度实体时必须选择主温度实体，不能由模型任意平均或选择。
- 移除主温度实体后清除该绑定，并要求选择剩余可用实体；尚未重新绑定时，房间温度为未知。环境内部仍可演化，但 Agent 无法凭内部真值判断目标已达到。

### 3.5 有人传感器

- 第一版提供仿真的人体存在信号，用户可在页面设置有人/无人或模拟人员进出，不接入摄像头与图像识别。真实存在传感器的硬件接入属于 M11 扩展。
- 仅提供有人/无人；未知、离线或过期读数必须保留其质量标记，不能当作无人。
- 不提供人数、身份、活动或睡眠判断。“卧室有人睡觉”来自用户明确说明或用户启用的睡眠偏好，不由占用信号推断。
- 默认每房间一个主占用读数；增加多个同类实体时显式设置主读数，避免隐式融合规则。
- 用户可在仿真页设置人员进入/离开。Agent 没有改写占用信号来满足目标的权限。

### 3.6 窗户传感器

- 仅提供窗户打开/关闭及读数质量。第一版没有开窗器，Agent 没有开窗或关窗动作。
- 能耗建议可指出开窗制冷的影响，并按用户限制请求手动关窗、等待或选择允许的其他动作；不能虚构“已经关闭窗户”。
- 用户在仿真页切换开合表示外界事件，会更新状态版本，供旧计划失效和重规划测试。
- 默认每房间监测一个窗户。用户添加多个窗户传感器时，所有已启用、已配置传感器均在线、读数有效且为关闭，才能报告“全部已监测窗户关闭”；任意一扇有效读数打开则报告存在开窗。没有已知打开但存在未知/离线读数时，总体开合为未知，仍逐项显示读数；没有配置传感器也视为未知。
- “已监测窗户全部关闭”不代表未配置传感器的真实窗户也被监测。

## 4. 公共字段与数据边界

每个实体至少记录内部 ID、家庭 ID、房间 ID、显示名称、实体类型、能力配置版本、是否启用、可用性、业务状态、状态版本、读数/状态时间。模板键作为可选来源信息保留。

用户可修改名称、归属、启用状态和该类型允许的配置参数；能力由支持的实体类型与驱动定义，不能通过填写任意 capability 为传感器增加写权限。第一版可从上述六种类型创建新实例，新设备类型需另行实现并验证驱动。

设备状态变化与房间/实体配置变化分别有版本。任务执行前重新检查实体存在、归属、启用状态、能力和相关状态版本；不能只依靠最初的自然语言名称定位动作目标。

新实体使用新的内部 ID。移除实体采用停用与归档，历史保留当时名称、归属和状态快照。移动实体会更新房间绑定及配置版本；主传感器随之移走时，原房间的主读数绑定清除。移除房间前要求迁移或归档其实体，不做隐式级联硬删除。

仿真状态 reset 保留用户当前的房间、实体清单、名称、归属和偏好，按各实体保存的初始参数重置运行状态并生成新的环境实例 ID。它不恢复被用户移除的默认设备。旧任务不能向 reset 后的环境写入，历史仍可读取。恢复默认模板属于不同操作，不与状态 reset 混用，第一版不提供隐式自动恢复。

## 5. 场景如何使用这些实体

| 场景 | 主要使用的实体 | 需要显式设置的场景事实 | 核验 |
| --- | --- | --- | --- |
| 回家准备 | 客厅空调、温度、窗户、灯和窗帘；卧室实体作为限制范围 | 到家目标时刻、舒适范围；如有人睡觉需显式说明并设置占用场景 | 客厅动作与目标时刻温度；卧室限制；无法完成的条件 |
| 睡眠模式 | 卧室灯、空调、窗帘、温度、窗户；其他房间用于保留项 | 用户启用睡眠场景、希望的温度和保留设备 | 灯和窗帘位置、空调状态、室温是否达到、例外保留 |
| 离家模式 | 用户指定范围内所有可控实体，结合占用信号和保留项 | 用户明确离家及关闭范围，不能仅从部分传感器推断全屋无人 | 应关闭设备与应保留设备；存在的故障和未知结果 |

正常模板初始值只代表初始家庭。具体演示/评测场景先复制并设置对应状态，不能因为模板默认卧室无人就忽略用户新提供的事实。用户说法与有效传感器冲突时，任务明确指出冲突并按场景规则澄清。

没有设备或传感器时，系统说明缺失能力。比如移除空调后不能凭空生成空调动作，移除温度传感器后不能凭空确认室温目标。相同房间内多盏灯既支持“全部灯”集合指令，也要求对无法定位的单个指令进行澄清。

仿真功率和累计能耗是环境根据各设备模型计算的派生指标，不计入默认十二实体，也不伪装成真实电表读数。室外环境参数、用户偏好和睡眠模式也不计入十二实体。

## 6. 第一版验收

- 两个新账号分别获得两房十二实体，内部 ID 和可变状态互不共享。
- 六种类型的读写权限、参数边界与初值可核查；传感器不能通过 Agent 写工具修改。
- 用户可增加房间，增添第二盏灯，重命名并移动设备；Agent 使用新的配置，不依赖固定中文房间名。
- 移除设备使涉及它的旧计划失效，但历史仍可回放；缺少传感器时保留未知状态。
- 未授权账号无法通过设备 ID、任务 ID、SSE 或检查点命名空间访问另一家庭。
- 仿真 reset 保留当前配置，不重新生成已移除的默认设备。
- 同样的快照、配置、事件、动作和时间序列产生同样的仿真结果；模型生成差异单独评测。
